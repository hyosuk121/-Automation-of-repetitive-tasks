# Hyoseok's Automation

경쟁사 앱 업데이트 조사 자동화를 먼저 제공하는 개인 관리자용 업무 포털입니다. 진입 화면은 파란색·보라색 헤더와 흰색 본문의 카드 캐러셀입니다. **경쟁사 앱 업데이트 조사 자동화**만 실행할 수 있고, Aircrew Monitoring은 준비 중입니다.

기존 로컬 프로젝트의 실제 소스/JSON이 제공되지 않아 전달된 전환 요청서를 기반으로 새로 구현했습니다. 기존 코드와의 동작 일치, 실제 데이터 이전 결과는 아직 검증되지 않았습니다.

## 구현된 기능

- PC/모바일 카드 탐색: 방향 버튼, 휠, 키보드, 터치 스크롤.
- Supabase 관리자 로그인: 서버 검증, HttpOnly 세션 쿠키, 허용 관리자 이메일, 변경 요청 Origin 검사.
- 경쟁사 등록·수정·보관, 국내/국외 구분, 드래그 및 버튼 정렬.
- App Store / Play Store 분리 대시보드, 검색·필터, 개별/전체 수집 요청.
- PostgreSQL 영속 작업 큐, 대상별 lease, 중복 실행 방지, 지수 백오프 및 중단 작업 회수.
- 한국 날짜별 최신 수치 스냅샷, 릴리즈와 설명 개정 이력, 시점별 수치 및 변경 이벤트.
- 이전 스토어 링크의 이력 보존, 보관된 경쟁사 이력 조회.
- CSV / Markdown / JSON / HTML / XLSX 내보내기와 KST 기간 필터.
- 기존 JSON/백업의 반복 실행 가능한 가져오기 명령.
- 기본 매일 오전 9시(KST) 수집. Vercel Cron이 날짜별 작업 키로 중복 등록을 방지하고 수집합니다.

UI에 임의의 경쟁사나 수집 성공 결과를 넣지 않습니다. 연결되지 않은 환경에는 연결 안내와 빈 화면이 표시됩니다.

## 구성

```text
Vercel: Vite 정적 화면 + Node.js API
   ├─ Supabase Auth: 관리자 인증
   ├─ Supabase PostgreSQL: 업무 데이터 + 작업 큐
   └─ 작업 생성 → Vercel 수집 API / Cron → Apple / Google 스토어
```

**Vercel + Supabase만으로 동작합니다. 별도 Worker 서비스 가입은 필요하지 않습니다.** 로그인한 수집 화면은 `/api/collections/process`를 앱 하나씩 호출합니다. 기존 대기 작업도 자동으로 이어서 처리하며, 각 요청은 결과 저장이 끝난 뒤 응답합니다. 관리자 화면에서 Supabase 자동 수집 설정을 적용하면 웹을 닫아도 5분마다 서버가 대기 작업을 이어서 처리합니다. 설정 전에는 화면을 열어 둔 동안만 수동 처리를 이어갑니다.

## 로컬 개발

Node.js 22.9 이상(검증 환경: Node.js 24), npm을 사용합니다.

```bash
npm ci
cp .env.example .env
# 아래 환경 변수 입력 후:
npm run db:migrate
npm run dev
```

다른 터미널 또는 별도 프로세스에서:

```bash
npm run worker
```

`npm run dev`는 Vite 4173, API 4174를 실행합니다. `.env`의 `APP_ORIGIN`은 브라우저에서 사용하는 출처와 정확히 같아야 합니다. 기본은 `http://localhost:4173`입니다.

Supabase가 없는 상태에서도 `npm ci && npm run dev`로 포털과 연결 안내를 확인하고, `npm test`로 임시 PostgreSQL에서 데이터 계층을 검증할 수 있습니다. 이 상태에서 실제 수집·저장은 할 수 없습니다.

프로덕션 로컬 실행:

```bash
npm run build
npm start
```

## Supabase 설정

현재 사용자 프로젝트에 맞춘 값과 연결 순서는 [배포 설정 안내](docs/deployment-settings.md)를 참고하세요. Supabase GitHub 연동용 설정과 SQL은 `supabase/` 표준 경로에 있습니다.

1. 프로젝트를 생성하고 Auth 설정에서 공개 회원가입을 비활성화합니다.
2. 관리자 이메일 계정을 생성합니다. 이메일·비밀번호 인증을 사용합니다.
3. 다음 변수는 서버/Worker의 보안 환경 변수로 설정합니다. `.env`를 커밋하지 마세요.

| 변수 | 용도 |
| --- | --- |
| `SUPABASE_URL` | Supabase 프로젝트 URL |
| `SUPABASE_ANON_KEY` | Auth 요청용 publishable/anon key |
| `DATABASE_URL` | PostgreSQL 연결 URL. 서버·Worker 전용 |
| `DATABASE_CA_CERT` | Supabase에서 다운로드한 CA 인증서의 PEM 전체. Vercel에서는 파일 경로 대신 이 변수 사용 |
| `DATABASE_CA_FILE` | 필요한 경우 DB 공급자의 검증 가능한 CA 파일 경로 |
| `ADMIN_EMAILS` | 허용 관리자 이메일. 쉼표로 구분 |
| `APP_ORIGIN` | 실제 웹 주소. 운영에서는 반드시 `https://...` |
| `CRON_SECRET` | Vercel Cron 인증값. 플랫폼 환경 설정에서 생성·입력 |
| `COLLECTION_INTERVAL_SECONDS` | 수동 재수집 최소 간격, 기본 300초 |
| `MAX_COMPETITORS` | 관리자별 활성 경쟁사 상한, 기본 100 |
| `SCHEDULE_HOUR_KST` | 하루 수집 시작 시각, 기본 9 |

`DATABASE_URL`은 브라우저에 노출하지 않습니다. API는 사용자를 인증하고 모든 조회·변경을 해당 사용자 ID로 제한합니다. 테이블은 RLS가 활성화되어 있고 브라우저용 정책은 열지 않습니다. 서버의 신뢰된 DB 연결이 필요합니다.

DB 연결은 TLS 인증서 검증을 유지합니다. URL에 `sslmode=no-verify` 같은 우회 옵션을 사용하지 마세요. Supabase 연결 메뉴의 호스트와 연결 방식을 사용하세요. Worker/마이그레이션에는 session pooler, 서버리스 API에는 transaction pooler를 사용할 수 있습니다. TLS 오류는 공급자의 CA와 올바른 호스트로 해결합니다.

`SELF_SIGNED_CERT_IN_CHAIN`이 발생하면 [인증서 등록 안내](docs/deployment-settings.md#db-인증서-오류가-나오는-경우)를 따라 `DATABASE_CA_CERT`를 등록합니다. 실제 줄바꿈 또는 `\n`으로 구분된 PEM을 지원합니다. 인증서는 관리자 화면에서 다운로드한 공식 CA를 사용하며, 서버 인증서 자체를 임의로 신뢰하거나 검증을 끄지 않습니다.

```bash
npm run db:migrate
```

`supabase/migrations/20261020000000_initial.sql`은 테이블, 고유 키, 인덱스, RLS 및 스냅샷 수정·삭제 방지 트리거를 생성합니다. 마이그레이션은 트랜잭션과 DB 잠금 안에서 실행되며 재실행할 수 있습니다. 실제 DB에 적용하기 전 별도 스테이징 프로젝트에서 확인하세요.

## Vercel 배포 (별도 Worker 불필요)

**자동 수집 · 과거 기록** 화면에서 새 DB 기능과 Supabase Cron을 한 번 적용합니다. 7월 9일 자료 연결 및 순위 설정은 [적용 안내](docs/automation-and-rankings.md)를 따릅니다.

1. 이 저장소를 Vercel 프로젝트에 연결합니다. 프로젝트 루트는 저장소 루트입니다.
2. `vercel.json`의 build command `npm run build`, output `dist`, Node API 설정을 사용합니다.
3. Vercel 환경 설정에 위 변수를 등록하고, `APP_ORIGIN`을 배포 도메인으로 지정합니다.
4. 스테이징 DB에 마이그레이션 후 API 조회 및 인증을 확인합니다.
5. Vercel에서 Fluid compute와 함수 실행 시간 300초 지원 여부를 확인합니다. `vercel.json`은 `maxDuration: 300`을 사용합니다.
6. 관리자 로그인 → 기존 대기 작업 자동 수집 → 이력 조회 → XLSX 다운로드를 실제 운영 도메인에서 확인합니다. 경쟁사 재등록은 필요하지 않습니다. 새 테이블은 자동 수집 설정 적용 시 생성됩니다.
7. 화면을 닫았다 다시 열어 대기 작업이 재개되는지 확인합니다. 실행 도중 종료된 작업은 3분 lease 만료 후 회수합니다.

Vercel Cron은 UTC 00:00(KST 09:00)에 `/api/cron`을 호출하여 작업을 등록하고 **직접 수집까지 수행합니다.** Hobby 플랜에서는 실행 시각이 해당 시간대 안에서 지연될 수 있습니다. Cron은 240초 동안 새 작업을 시작하고 남은 시간은 진행 중인 작업 저장에 사용합니다. 등록 앱 수와 스토어 응답 속도에 따라 한 번에 전부 끝나지 않을 수 있습니다. Supabase 자동 수집 설정을 적용하면 남은 작업과 지연 재시도는 다음 5분 호출에서 이어서 처리합니다. 설정 전에는 다음 대시보드 접속 또는 다음 일일 Vercel Cron에서 처리합니다. 별도 서비스 없이 무제한 백그라운드 실행을 보장하지는 않습니다.

수동 수집은 브라우저당 한 앱씩 처리합니다. 인증된 관리자의 작업만 가져오며 여러 탭/Cron의 중복 처리는 DB 잠금과 lease 토큰으로 방지합니다. 스토어 요청 타임아웃은 18~20초이며 App Store는 조회와 이력 요청이 각각 실행됩니다. 네트워크/5xx/429 오류는 최초 시도 이후 최대 3회 지연 재시도합니다. 한 앱의 실패가 다른 앱의 결과를 취소하지 않습니다.

`npm run worker`는 로컬에서 선택적으로 사용할 수 있는 기존 실행 방식으로 남겨 두었습니다. 운영에 필수는 아닙니다.

## 과거 기록 보존 방식

- 수집 작업/대상 조합별 처리 영수증으로 중복 실행을 방지합니다. 수치는 앱별·한국 시간 날짜별 최신 한 건만 저장하며, 늦게 가져온 과거 자료가 최신 수치를 덮어쓰지 않습니다.
- 일별 스냅샷은 최신 수치로 갱신할 수 있고 직접 DELETE는 차단합니다. 릴리즈, 설명 개정 이력, 변경 이벤트는 별도로 누적 보존합니다.
- `20261022000000_daily_snapshots.sql`은 같은 날짜의 기존 중복 수치를 최신 한 건으로 합치고 이력 참조를 연결합니다. 배포 후 첫 인증 API 요청 또는 수집 저장 시 트랜잭션 안에서 자동 적용됩니다. 별도 SQL 실행은 필요 없습니다.
- App Store 버전 목록을 완전하게 파싱한 경우에만 미확인 릴리즈를 표시합니다. Lookup fallback은 부분 성공이며 기존 릴리즈의 상태를 바꾸지 않습니다.
- Play Store의 최신 설명이 확인되면 이전 설명은 이력으로 남고 현재 응답에서 미확인 상태로 전환됩니다. 버전 번호는 스토어 응답에 명시된 경우에만 저장하며, VARY/기기별 상이 등은 null로 보존합니다.
- `missing_since`는 실제 삭제일이 아닌 **처음 미노출을 관측한 시점**입니다.
- 스토어 링크의 앱 ID/국가/언어가 바뀌면 별도 수집 대상을 만듭니다. 상세 화면에서 이전 연결 이력도 선택할 수 있습니다.
- JSON 가져오기에서는 과거 파일 간 순서가 불명확하므로 변경 이벤트를 추정하지 않고 날짜별 최신 수치와 릴리즈 사실을 보존합니다.

## 기존 JSON 가져오기

실제 파일은 저장소에 포함하지 말고 안전한 위치에 보관하세요. 관리자 UUID는 Supabase Auth 사용자 ID입니다. 첫 파일은 현재 `apps.json`, 이후 파일은 백업입니다.

```bash
npm run import:json -- <관리자-UUID> /secure/apps.json /secure/apps.json.bak
```

- 최상위 배열 또는 `{ "apps": [...] }`를 지원합니다.
- 중첩 `appStore` / `playStore`를 우선하며 App Store legacy 최상위 레코드도 지원합니다.
- `recordId`/`id`로 경쟁사를 식별하고, 없으면 플랫폼·스토어 ID·국가 조합을 사용합니다.
- `refreshedAt`이 없거나 잘못된 레코드는 파일 전체를 롤백하며 임의 시각을 만들지 않습니다.
- 현재 파일의 이름·구분·순서를 유지합니다. 백업에만 존재하는 경쟁사는 보관 상태로 가져옵니다.
- 파일 해시/레코드/수집 대상별 작업 키로 같은 파일의 재실행을 중복 처리하지 않습니다.
- 명령은 원본 파일을 읽기만 하며 삭제하거나 수정하지 않습니다.

실제 레거시 소스/JSON이 미제공 상태이므로 먼저 사본으로 실행해 경쟁사·플랫폼·릴리즈 개수와 정렬을 원본에 대조해야 합니다. 기존 파일의 필드가 다르면 `lib/importer.js` 매핑을 조정해야 할 수 있습니다. 이전 중에는 Worker를 중지해 현재 데이터와 혼합 수집하지 않도록 하세요.

## 검증

```bash
npm test
npm run build
npm run test:browser
npm audit --omit=dev
```

- `npm test`: PGlite의 실제 PostgreSQL SQL 실행을 이용하는 단위·통합 테스트. 실제 Supabase 서비스에 연결하지 않습니다.
- `test:browser`: Chromium에서 PC/모바일 카드, 비활성 카드, 키보드 이동, 등록·수집·이력·내보내기·수정·보관을 검증합니다. 테스트에 한해 임시 DB와 주입된 사용자/스토어 결과를 사용합니다. 운영 서버에 테스트 인증 경로는 없습니다.
- Chromium 경로는 기본 `/usr/bin/chromium`이며 `CHROMIUM_PATH`로 지정할 수 있습니다. 없으면 `npx playwright-core install chromium`으로 설치할 수 있습니다.
- 스크린샷/내보내기 검증 파일은 Git에서 제외된 `test-results/`에 생성됩니다.

## 현재 검증 범위 및 제한

- 빌드, 로컬 SQL 테스트, 브라우저 테스트는 현재 환경에서 실행합니다. 최종 실행 결과는 `docs/verification.md`에 기록합니다.
- Supabase/Vercel 자격증명이 제공되지 않아 **실제 로그인, 운영 DB 적용, 공개 배포, 예약 실행, 운영 DB 백업 복구는 미검증**입니다.
- 현재 클라우드 네트워크에서 `itunes.apple.com`, `apps.apple.com`, `play.google.com` 접근이 프록시 HTTP 403으로 차단되었습니다. 실제 스토어 수집 smoke test는 배포 환경에서 반드시 실행해야 합니다. 허용목록을 관리한다면 이 도메인들을 기존 허용목록에 추가하세요.
- Apple 버전 기록과 Google Play 데이터는 외부 HTML 구조에 의존합니다. 파서 실패를 부분 성공/실패로 표시하고 기존 기록을 보존합니다.
- 앱별 시계열은 현재 표로 제공합니다. 차트와 변경 알림은 구현하지 않았습니다.
- 초기 내보내기는 50,000행 제한입니다. 큰 범위는 기간을 나누어 추출하세요.
- 플랫폼 요금, 선택적 Worker 비용, Supabase 백업/PITR 보존 기간은 사용자가 선택한 플랜에 따라 다릅니다.

## 백업·복구 운영

Supabase의 백업 또는 PITR 기능을 사용 중인 요금제에서 확인하고 복구 보존 기간을 정하세요. 운영 전 스테이징 복구 절차:

1. Worker를 중지하고 복구 기준 시점을 기록합니다.
2. Supabase의 공식 복구 기능으로 별도 프로젝트에 복원합니다.
3. 경쟁사·스냅샷·릴리즈 개수와 알려진 과거 릴리즈/개정 내용을 확인합니다.
4. 복원 프로젝트에 앱을 연결하여 로그인·조회·내보내기를 검증합니다.
5. 중단된 작업의 lease 회수 및 중복 없는 수집을 확인한 후 Worker를 다시 시작합니다.

백업 기능이 켜졌다는 이유만으로 복구 검증이 완료된 것으로 간주하지 않습니다. 외부 스토어 이용 약관과 허용 요청 빈도도 운영 전에 확인하세요.

### 공개 조회와 로딩

- 비로그인 방문자는 대시보드, 활성 경쟁사의 릴리즈·수치·변경 이력, 카테고리 순위를 조회할 수 있습니다. 등록·수정·보관·수동 수집·가져오기·내보내기·설정·작업 로그는 관리자 전용입니다.
- 공개 대상은 `ADMIN_EMAILS`의 **첫 번째 이메일**에 해당하는 Supabase Auth 계정입니다. 다른 계정의 작업 공간을 공개하려면 서버 환경 변수 `PUBLIC_OWNER_ID`에 해당 계정의 UUID를 지정합니다. URL의 소유자 파라미터로 공개 대상을 바꿀 수 없습니다. 기본 관리자 한 명인 기존 배포에서는 별도 설정이 필요 없습니다.
- `/api/public/*`는 GET만 허용합니다. 보관된 경쟁사는 제외하고, 계정 ID·작업 ID·수집 원본·내부 오류를 공개 응답에서 제외합니다. Supabase RLS를 해제하거나 브라우저에 DB 비밀 키를 전달하지 않습니다.
- 공개 응답은 CDN에서 30초 캐시하고 추가 30초 동안 기존 응답을 제공하며 갱신할 수 있습니다. 따라서 방문자에게 최신 수치가 표시되기까지 약 1분 지연될 수 있습니다. 관리자 API는 계속 `no-store`입니다.
- 대시보드는 목록과 순위를 병렬로 불러와 준비된 영역부터 표시합니다. 수집 작업 로그는 해당 화면에서만 요청하고, 자동 실행 설정은 처음 또는 설정 화면에서 요청합니다. 이력 창은 앱 정보와 기록을 한 응답으로 받습니다. DB 준비 확인은 서버 인스턴스당 성공 후 재사용하고, Excel 모듈은 내보낼 때만 로드합니다.
- Vercel 실행 지역과 Supabase 지역은 이번 변경에서 옮기지 않았습니다. 실제 네트워크 응답 시간은 배포 후 운영 로그로 확인해야 합니다.


### 이력·평점·차트 표시

- 릴리즈 이력은 공개일 내림차순으로 조회하며, 공개일이 없는 기록은 뒤에 표시합니다. 팝업 제목과 닫기는 고정하고 업데이트 설명은 항상 펼쳐 둡니다.
- 화면과 내보내기의 평점은 소수 둘째 자리까지 반올림합니다. 원래 수집 정밀도는 DB에 유지합니다.
- 시점별 수치에는 한국 날짜 기준 일별 평점 차트를 제공합니다. 평점이 없는 관측에는 점을 그리지 않습니다.
- 사용자 확인에 따라 **2026-07-09(KST)의 모든 앱 평점과 평가 수만 삭제**합니다. 해당 날짜의 릴리즈, 설명 개정, 리뷰 수, 다운로드 정보 등은 유지합니다. `20261023000000_remove_july_ratings.sql`은 최초 관리자 API 요청 또는 다음 자동 실행에서 적용되며, 동일 날짜를 재가져와도 삭제한 평점·평가 수가 복원되지 않도록 합니다.
- 순위 차트의 사용자 지정 기간은 오늘까지 최대 366일입니다. 차트와 일별 표는 각각 경쟁사를 여러 개 선택할 수 있습니다. 일별 미수집 항목은 `-`, 수집 실패와 순위권 밖은 구분해서 표시합니다.
- 대시보드의 업데이트 내용 버튼은 앱 행 바로 아래에 전체 폭의 내용을 열고 다시 접을 수 있습니다. 프로젝트 표시명과 초록 번개 SVG 아이콘도 변경했습니다.

### Play Store 관측 이력 정리

- Play Store는 현재 공개된 업데이트를 수집할 때부터 누적합니다. 업데이트 날짜가 있으면 설명이 없어도 릴리즈를 저장하고 화면에 `제공된 설명 없음`을 표시합니다. 같은 날짜·버전의 설명 변경은 개정본으로 보존합니다.
- 7월 9일 보고서 가져오기는 App Store만 지원합니다. `20261024000000_play_observed_history.sql`은 2026-07-09(KST)의 **가져오기 작업에서 생성된 Play Store 관측**과 그 관측에만 있는 릴리즈를 제거합니다. 실제 수집된 Play Store 기록과 App Store 릴리즈는 유지합니다.
- 기존 실제 수집 스냅샷에 업데이트 날짜가 있으면 누락된 릴리즈를 복원합니다. 이미 사라져 저장되지 않은 스토어 과거 기록을 추정해 만들지는 않습니다.
- 배포 후 최초 관리자 API 요청 또는 다음 자동 실행에서 트랜잭션으로 한 번 적용됩니다. 별도 SQL 수동 실행은 필요 없습니다.
