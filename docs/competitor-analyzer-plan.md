# 통합 자동화 포털 — Competitor Analyzer 1차 개발 명세

상태: 구현 기준 명세. 현재 코드와 검증 범위는 README.md 및 verification.md를 참조한다. 기존 소스, 데이터, Supabase 연결 및 배포 환경은 아직 제공되지 않았다.

## 1. 목표와 범위

로컬에서 CMD로 실행하던 도구를 웹에서 사용할 수 있도록 통합한다. 첫 출시에서는 `competitor_analyzer`만 활성화한다. `aircrew_monitoring`은 준비 중 카드로 노출하고 기능 구현은 후속 단계로 둔다.

웹은 Vercel에 배포하고 로그인, 영속 데이터 및 이력은 Supabase를 사용한다. 기존 프로젝트의 UI 흐름과 핵심 동작을 유지하되, 파일 기반 최신 상태 저장을 시점별 기록 보존 구조로 전환한다.

## 2. 진입 페이지

- 경로: `/`
- 제목: 업무 자동화
- 안내: 필요한 도구를 선택해 시작하세요.
- 사용자가 최종 제공한 카드 이미지를 기준으로 파란색·보라색 헤더, 원형 아이콘, 흰색 본문, 짙은 둥근 실행 버튼을 적용한다. 유리 질감은 사용하지 않는다.
- 중앙 카드와 인접 카드가 보이는 가로 캐러셀로 구성한다. 모바일에서도 스와이프하여 다음 카드를 탐색한다.
- 최초 선택은 `경쟁사 앱 업데이트 자동화`이다.
- 중앙 카드에는 아이콘, 제목, 짧은 설명, 상태, 실행 버튼을 표시한다.
- 휠, 터치 스와이프, 이전·다음 버튼, 키보드로 카드 선택을 변경한다. 스크롤만으로 기능을 실행하지 않는다.
- 첫 버전은 아래 두 카드를 표시한다. 미정의 도구를 실제 제공 기능처럼 만들지 않는다.

| 카드 | 상태 | 선택 시 동작 |
| --- | --- | --- |
| 경쟁사 앱 업데이트 자동화 | 사용 가능 | `/competitor-analyzer`로 이동 |
| Aircrew Monitoring | 준비 중 | 탐색은 가능하지만 실행 및 페이지 이동은 비활성화 |

카드 수가 적더라도 순환 탐색할 수 있게 한다. 시각적 반복 카드가 필요하면 접근성 트리와 키보드 순서에는 실제 항목만 노출한다. 준비 중 상태는 색상뿐 아니라 텍스트로 표시하고 비활성 실행 버튼의 상태를 명확히 한다. 모션 감소 설정에서는 회전·확대 애니메이션을 줄인다.

## 3. 분석 도구 화면

경로는 `/competitor-analyzer`를 기본으로 한다. 실제 작업 화면은 앞서 제시된 밝은 대시보드 스타일을 사용한다.

공통 구성:

- 왼쪽 사이드바: 도구 홈으로 돌아가기, 대시보드, 경쟁사 관리, 수집 이력.
- 상단: 페이지 제목, 최근 성공 수집 시간, 전체 수집, 경쟁사 등록.
- App Store / Play Store 탭으로 플랫폼별 결과 분리.
- 이름 검색, 국내/국외 필터, 변경 및 오류 상태 필터.
- 경쟁사명, 앱 정보, 버전/업데이트일, 평점, 변경 상태, 마지막 수집 상태를 표시하는 표.
- 값이 확인되지 않으면 `- (알 수 없음)` 표시. Play Store 버전과 랭킹을 추정값으로 채우지 않는다.
- 최초 데이터가 없으면 경쟁사 등록을 안내하며 실제 데이터처럼 보이는 샘플 결과를 넣지 않는다.

경쟁사 관리:

- 이름, 국내/국외 구분, App Store 및 Play Store 링크 등록·수정.
- 최소 하나의 유효한 스토어 링크 필요.
- 저장 후 수집 작업을 생성하고 진행 상태 표시.
- 개별 및 전체 수집, 드래그 정렬과 접근 가능한 순서 변경 버튼.
- 제거는 보관 처리. 과거 결과는 이력에서 조회 가능.

앱 상세:

- 최신 정상 데이터 및 마지막 성공/실패 시점.
- 수집 시점별 스냅샷.
- 현재 노출 및 과거에 관측된 릴리즈 타임라인.
- 릴리즈 설명 개정 이력.
- 평점, 평가 수, 리뷰 수 추세. 다운로드 구간은 원문을 보존하며 정확한 수치처럼 그래프화하지 않는다.
- 기간 필터, 변경 이벤트, 수집 오류.

내보내기:

- CSV, Markdown, JSON, HTML, XLSX.
- 최신 현황, 전체 릴리즈, 기간별 스냅샷, 변경 이벤트.
- 생성 시각, 조회 기간, 기준 시간대 `Asia/Seoul` 명시.

## 4. 배포 구조

```text
브라우저
  └─ Vercel: 포털 / 분석 UI / 인증된 API
       ├─ Supabase Auth
       ├─ Supabase PostgreSQL: 대상, 작업 큐, 스냅샷, 이력
       └─ 수집 작업 등록
            └─ Worker / Scheduler
                 ├─ Apple Lookup / App Store
                 └─ Play Store
```

Vercel은 사용자 요청을 받아 수집 작업 ID를 빠르게 반환한다. 긴 전체 수집은 웹 요청이 계속 열려 있는 동안 수행하는 방식에 의존하지 않는다.

작업 실행기는 별도 장기 실행 Worker를 기본 설계로 한다. 기존 코드의 실제 수집 시간, 대상 규모, Vercel 요금제 실행 제한을 측정한 후 짧은 배치형 서버리스 실행으로 대체 가능한지 판단한다. 실행 플랫폼은 미확정이며 Vercel만으로 모든 수집이 가능하다고 가정하지 않는다.

## 5. 데이터 및 이력 보존

요청서의 핵심 테이블:

- `competitors`: 경쟁사와 정렬 순서, 보관 시각.
- `store_apps`: 플랫폼별 수집 대상 및 지역/언어.
- `collection_runs`: 전체 실행 단위.
- `store_snapshots`: 매 성공 수집의 정규화 결과. append-only.
- `release_history`: 관측한 릴리즈 및 노출 상태.
- `release_note_revisions`: 업데이트 설명의 개정본.

운영에 추가로 필요한 테이블:

- `collection_items`: 대상별 작업 상태, 시도 횟수, 오류, 다음 시도 시각, 잠금 만료 시각.
- `change_events`: 스냅샷 사이의 변경 이벤트.
- `migration_imports`: 원본 파일 해시와 레코드 식별 정보로 재실행 중복 방지.

보존 규칙:

1. 동일 내용도 수집 시점마다 스냅샷을 남긴다. 단, 동일 작업의 재시도는 중복 저장하지 않는다.
2. 스토어 링크가 다른 앱을 가리키도록 변경되면 기존 수집 대상을 비활성화하고 새 대상을 만든다. 다른 앱의 이력을 섞지 않는다.
3. 평점이나 설명이 바뀌어도 이전 스냅샷과 개정본은 유지한다.
4. 요청 실패 또는 부분 파싱은 마지막 정상 데이터나 릴리즈의 부재를 확정하지 않는다.
5. 버전 기록을 온전히 수집한 응답에서만 과거 릴리즈가 이번 응답에 없는지 판정한다. Lookup 최신 버전만 확보한 fallback은 `부분 성공`으로 기록한다.
6. `missing_since`는 실제 삭제 일자가 아니라 수집기가 처음 미노출을 관측한 시점이다. UI도 “스토어 응답에서 미확인”처럼 관측 사실을 표현한다.
7. Play Store의 이전 “새로운 기능”이 교체되더라도 해당 설명과 날짜를 이력에 유지한다.
8. DB 권한으로 일반 사용자/API의 스냅샷 UPDATE·DELETE를 제한한다.

## 6. 수집 처리와 복구

- 기본 하루 1회, 수동 개별·전체 수집 지원.
- 동일 대상의 동시 실행은 DB 작업 claim 및 만료 가능한 lease로 제어.
- 외부 요청은 타임아웃 적용. 일시적 네트워크/서버 오류는 최대 3회 재시도.
- 429는 Retry-After를 존중하고 요청을 지연한다. 파서 오류 및 영구 오류는 무작정 반복하지 않는다.
- 대상별 작업 실패가 다른 대상의 성공 저장을 막지 않도록 한다.
- Worker 재시작 후 만료된 실행 작업을 회수해 재시도한다.
- 외부 HTTP 수집은 DB 트랜잭션 밖에서 수행한다. 수집 결과의 스냅샷·릴리즈·개정·변경 이벤트와 대상 작업 완료 기록은 하나의 짧은 트랜잭션으로 저장한다.
- 완료 상태는 실제 대상 결과를 집계해 성공·부분 성공·실패로 구분한다.

## 7. 인증 및 운영 기본값

- 개인 관리자 1명. 공개 회원가입은 제공하지 않고 허용된 관리자만 사용.
- 조회·내보내기·변경·수집 API 모두 인증과 권한 검사.
- Supabase RLS 적용. service-role 키는 서버/Worker에만 저장.
- 쿠키 기반 인증은 HttpOnly, Secure, SameSite와 변경 요청 출처 검증 적용.
- 스토어 URL은 허용 호스트와 ID 형식 검증 후 서버에서 공식 URL로 재구성. 임의 URL 수집 금지.
- API 입력 크기 제한, 실행 요청 속도 제한, 구조화 오류 로그.
- 정규화 데이터 무기한 보존, raw HTML 장기 보관 안 함.
- 변경 알림은 초기 범위 제외.
- 백업 주기·복구 가능 기간은 선택한 Supabase 요금제에서 확인하고 복구 절차 검증.
- 운영/스테이징 자격증명과 DB 구분.

## 8. 기존 데이터 이전

원본 JSON과 백업을 수정하지 않고 읽는다. 현재 목록의 정렬 순서를 유지하고, 중첩된 `appStore` / `playStore` 데이터를 우선한다. 각 파일의 실제 수집 시각을 기준으로 스냅샷 및 릴리즈 이력을 병합한다.

시각이 없거나 모호하면 임의로 과거 사실을 만들지 않고 데이터 품질 경고로 기록한다. 파일의 수정 시각을 실제 수집 시각이라고 단정하지 않는다.

마이그레이션 재실행 시 스냅샷과 릴리즈가 중복되지 않아야 한다. 경쟁사 수, 스토어 연결 수, 버전 수, 정렬 순서를 원본과 대조한다. 검증 후에도 원본은 별도 보존한다.

## 9. 구현 순서와 검증

1. 기존 소스·테스트·실제 JSON 구조 확인 및 현재 기능 실행.
2. 포털 카드와 분석 도구 공통 레이아웃, 라우팅 구성.
3. Supabase 인증·권한·스키마와 JSON 마이그레이션.
4. 기존 파서 연결, 작업 큐, 대상별 원자적 저장 및 재시도.
5. 대시보드·상세·이력·내보내기 연결.
6. 실제 스토어 수집, 자동 수집, 재시작 복구, 배포 검증.

필수 테스트:

- 활성 카드 이동, 준비 중 카드 실행 차단, 키보드·터치·모션 감소 동작.
- 미인증 및 비관리자 요청 차단.
- 신규 릴리즈, 설명 수정, 미노출 및 재등장 보존.
- 부분 파싱에서 잘못된 미노출 처리 방지.
- 한 플랫폼 실패 시 다른 플랫폼과 직전 정상 결과 보존.
- 동시 수집, 재시도 멱등성, Worker 복구.
- JSON 이전 재실행, 원본 개수 및 정렬 일치.
- 기간 조회와 내보내기 파일 검증.
- 실제 App Store / Play Store 각 1개 수집.
- 재배포 후 데이터 유지, 예약 작업 실제 실행, 백업 복구.

## 10. 아직 필요한 입력

- 기존 `competitor_analyzer` 소스와 테스트.
- `data/apps.json` 및 이전할 백업. 비밀값은 제외.
- Supabase 프로젝트 연결 및 안전한 환경 변수 설정.
- Vercel 연결 및 수집 Worker 실행 플랫폼/예산.
- 실제 대상 수를 바탕으로 초기 수집 상한과 처리량 결정.

본 문서 저장은 애플리케이션 구현, 실제 데이터 마이그레이션, 환경 설정 저장 또는 배포 완료를 의미하지 않는다.
